# AdaptFit V0.2 — Architecture

## 1. Phase 0 audit (baseline before V0.2)

**Baseline (V0.1, commit-less working tree, snapshot kept outside the repo):** lint ✅, typecheck ✅, 132 Vitest tests ✅, 10 Playwright tests ✅, ~4.5k lines of TypeScript.

| Area | V0.1 state | V0.2 decision |
|---|---|---|
| Recommendation | Deterministic generic workout generator (time/energy/equipment) | **Kept**, but only as an explicitly chosen "Quick adaptive workout". Never substitutes for a user's programme. |
| Programmes | None — every day was a generated workout | New: user programmes, days, exercises, rep ranges, priority lifts, rotation, shortened/adjusted versions with approval. |
| Logging | One form per set; tapping "Log set" saved the prefilled prescription immediately | New: per-set rows prefilled from the previous comparable session, **explicitly confirmed** one tap at a time; steppers; add/delete/skip; pause/resume. |
| Loads | `{value, unit}` with no loading convention | Explicit `loadType` (total / per-side / per-dumbbell / bodyweight / bodyweight-plus / assisted / timed). Never compared across conventions. |
| Duration | `completedAt − startedAt` shown as workout length | Explicit `durationSource` (timer / manual / not-recorded / legacy-entry-time). Implausible timer values default to "not recorded". |
| Progress | XP = 20 × workouts; stats = session counts | Progression engine (comparisons, PRs, trends), plateau detection, deterministic RPG layer (STR/END/REC/CONS, achievements, missions). |
| Storage | Dexie v2 (profile, checkIns, sessions, meta) | Dexie **v3** + new tables; non-destructive migration with verbatim legacy copies. |
| UI | 3 tabs (Today/History/Character), basic dark theme | 4 tabs (Train/Progress/Coach/Journey) + Settings; Premium Pixel Hybrid design system. |

### Data audit findings (History screenshots)

The owner's database lives in their browser and was not accessible to the build, so findings come from reproducing V0.1 behaviour in Playwright against the V0.1 build:

1. **"26 sets completed in 1 minute."** In V0.1 the set form was prefilled with the plan's reps, and each tap of *Log set* saved a set immediately; extra sets beyond the plan were allowed. A script reproduced **23 sets in ~5 seconds** (`23/13 sets logged`). The sets were therefore *explicitly saved by taps*, but V0.1 had no way to distinguish "performed" from "entered quickly", and the displayed duration was simply start→finish (i.e. data-entry time). **Conclusion:** consistent with retrospective/rapid entry, not a one-minute workout. V0.2 marks such records `legacy-entry-time` and shows "Duration not recorded".
2. **"Identical 30 kg across exercises."** V0.1 carried the load forward between sets *of the same exercise* only; when the next exercise opened, the load field was blank (verified: `loadAfterAdvance: ""`). Repeated 30 kg values across different exercises must have been typed. They are **not** generated by the app. Because V0.1 never recorded *how* a load was applied (per side? per dumbbell? total?), migrated V0.1 loads are kept but marked `unspecified` and only compared with other `unspecified` records of the same exercise.
3. **Were sets generated automatically?** No. Every V0.1 set required a tap. V0.2 additionally requires a deliberate check per set; prefilled values are never completed and are dropped at finish if unconfirmed.

To audit the actual records, export a V0.1 backup (see README, "Before upgrading") — the JSON shows each set's `loggedAt` timestamp.

## 2. Layers

```
src/domain/    Pure, deterministic logic (no I/O, time passed in)
  types.ts        Data model (Profile, Programme, WorkoutSession, CoachRecommendation, WeekPlan…)
  loads.ts        Loading conventions, formatting, unit conversion, comparable keys
  programme.ts    Programme ops, estimates, rotation, shortened day, next planned session
  workout.ts      Session building/prefill, set transitions, timer, finish, corrections, duration text
  progression.ts  Summaries, comparisons, PRs, history series, ranges, weekly consistency
  plateau.ts      Possible-plateau assessment with evidence, missing data, ≤2 questions
  coach.ts        Recommendations from findings/answers, decisions, apply change, weekly review
  schedule.ts     Reduced-week proposals preserving priority lifts with trade-offs
  notesImport.ts  Notes and routine parsers, unresolved-issue checks, import builder + hash
  rpg.ts          XP events, levels, stats, achievements, missions, unlocks
  migrate.ts      V0.1 → V0.2 record conversion (used by DB upgrade and v1 backups)
  recommend.ts    V0.1 quick-workout engine (opt-in only)
src/data/      Dexie schema/migrations, transactional repositories, Zod schemas, backup v2
src/features/  train, workout, history, progress, coach, journey, settings, programmes, importer, onboarding
src/ui/        Design tokens, CSS, controls, charts, dialog, announcer, pixel adventurer sprites
```

All screens read one live snapshot (`useAppData`, Dexie `liveQuery`), so progress, PRs, XP, and achievements are **always derived from stored records**. Editing or deleting a session immediately reconciles everything; there is no stored XP balance to drift.

## 3. Key rules

- **Programme first.** If an active, valid programme exists, Train shows its next day (rotation, or the approved adjusted week). Generic workouts appear only behind an explicit "Quick adaptive workout" button when no programme exists.
- **Approval required** for every change: shortened sessions, adjusted weeks, coach programme changes. Rejecting leaves the programme byte-for-byte unchanged (tested).
- **Comparability.** `exerciseId + loadType`; kg/lb converted, conventions never mixed; assisted loads compare inversely; first record is a baseline, not a PR; missing load → "insufficient".
- **Plateau.** ≥4 comparable sessions in 6 weeks, spanning ≥14 days, no gap >14 days, and no improvement over the best earlier performance. One bad session cannot trigger it. Automatic recommendations: priority lifts only, max 2/week; others listed under "Worth watching".
- **XP.** +20 completed workout (≥1 completed set), +10 planned/adjusted programme session, +15 per PR (≤3/session), +25 planned week met, +5 recovery check-in (≤3/week), +5 weekly review. Workouts beyond the week's plan earn no workout XP. Unique event keys prevent duplicates. Level n→n+1 needs `100 + 50(n−1)` XP.

## 4. Storage and migration

### Schema versions

| Version | Tables | Notes |
|---|---|---|
| 1 | profile, checkIns, sessions | V0.1 initial |
| 2 | + meta; session indexes | V0.1 |
| **3** | + programmes, customExercises, recommendations, weekPlans, measurements, **legacySessions**; sessions index `importHash` | V0.2 |

### Migration plan (v2 → v3), executed in Dexie's upgrade transaction

1. Read the existing profile; add `timezone` (device), `gamification: true`, empty `lifestyle`.
2. Add optional recovery fields (`sleepHours`, `fatigue`, …) as `null` to every check-in.
3. For every non-V3 session: **copy the original record verbatim into `legacySessions`**, then replace it with the V3 shape (`migrateSession`): plan items → session exercises, logged sets → completed sets (same IDs, values, timestamps), loads `unspecified`, duration `legacy-entry-time`.
4. Dexie runs the whole upgrade in one transaction: if anything throws, the database stays at v2 untouched.

Validation: unit test T37 (pure conversion), integration test "Database migration v2 → v3" (real upgrade with a v2 database), and backup-v1 restore tests.

### Rollback / safety

- Before first opening V0.2, export a backup from V0.1 (README explains how — the old service worker keeps serving V0.1 until you tap *Refresh*).
- After upgrading, `legacySessions` still holds every original V0.1 session and is included in V0.2 exports.
- V0.2 restores **both** backup format 1 (V0.1) and 2.

### Backup format 2

`{ format: "adaptfit-backup", version: 2, exportedAt, data: { profile, checkIns, sessions, programmes, customExercises, recommendations, weekPlans, measurements, reviewedWeeks, legacySessions } }`. Restore = size check (5 MB) → JSON parse → Zod schema → cross-record consistency (duplicate IDs, one active workout/programme, valid states, duplicate imports) → preview + confirmation → single transaction (rolls back on failure).

## 5. Privacy and security

No network calls at runtime, no external fonts/scripts (Inter is bundled), strict production CSP, imported text rendered as text, personal data only in IndexedDB (never in service-worker caches).

## Scheduling discrepancy — root cause

V0.2 computed "planned sessions" in two ways:
- the weekly review used `programme.daysPerWeek`;
- the week planner and `proposeWeek()` used `min(daysPerWeek, days.length)`.

A programme with fewer distinct days than weekly sessions (e.g. one day done 3× a week) therefore showed "1 of 3 planned" next to "Normally 1 sessions".

The fix in V0.3:
- `weekSchedule()` returns `defaultFrequency` (programme sessions per week), the approved temporary `adjusted` plan, `planned`, `completed`, and `remaining`. Train, Coach, Progress, and XP use it via `targetForWeek()`.
- `proposeWeek()` repeats days to fill the week.
- Adjusted-week matching counts repeated days.
- Text is pluralised.

Plateau assessment gained a `stable` state. Insights only says "No plateau detected" when at least one lift has enough history; otherwise it says what data is missing.

The upgrade runs in one Dexie transaction:
1. It copies the profile, programmes, and measurements it will change to `meta['snapshot:pre-v0.3']`.
2. It adds the new fields with defaults.
3. It moves bodyweights into the new table.

Tested with fake-indexeddb (T58: the v3 → v4 upgrade preserves sessions, XP, and achievements, creates the snapshot, and moves bodyweight) and end-to-end via V0.2 backup restore (T80).

### Rollback

1. Before upgrading, export a V0.2 backup (V0.2 → Settings → Export backup).
2. To go back, build a copy of the V0.2 source (the project has no commits yet, so keep a copy of the V0.2 folder), open it at a **different address or after clearing site data** (a v4 database can't be opened by V0.2), and Restore the V0.2 backup.
3. If no V0.2 backup exists, the pre-upgrade copy of the changed records is in IndexedDB at `adaptfit → meta → snapshot:pre-v0.3`. Sessions and check-ins were never changed by the upgrade.

# V0.4 — Intelligent Workout Notebook (2026-11-08)

V0.4 is a product pivot, not a rebuild. The React/TypeScript/Dexie stack, the
domain modules (progression, plateau, coaching, schedule, guided programmes,
nutrition, bodyweight, backup) and all stored data were kept. What changed is the
everyday experience: the plan is a **note**, progress is recorded with a
**weekly update**, and analysis runs on confirmed records.

## Notes editor

- **Display:** day headings (amber small caps), each exercise as two lines —
  name, then `3 sets × 8 reps — 30 kg/side` — plus notes, plus a faint
  `Last (w/c 26 Oct): 30 kg/side × 7, 7, 6` from real history.
- **Inline editing:** tapping a line turns it into a text box containing exactly
  what was shown. On Done, leaving the field, switching app, or locking the
  phone, the text is parsed (`parseExerciseBlock`) and saved. IDs are kept, so
  history and coaching links survive. A bare `35 kg` keeps the exercise's
  established convention; a new exercise with an unclear convention is
  flagged, never assumed.
- **Edit as text:** a whole day as one text box (`parseDayText`) for adding,
  removing, reordering or pasting several lines; exercises are matched to the
  existing ones by identity or name.
- **Uncertain fields** appear as amber questions with one-tap answers (total /
  per side / per dumbbell / added / assisted; kg / lb; keep name).
- **Reliability:** every keystroke is mirrored synchronously to
  `localStorage` (`adaptfit:draft:*`) and restored after refresh or a crash
  ("Restored your unsaved edit"); saves are IndexedDB transactions with a
  revision; status shows Saving… / Saved / Not saved; Undo button and an undo
  toast for removals; destructive deletes (note, day) need confirmation.
- No background execution is claimed: saving uses `visibilitychange` and
  `pagehide`, which iOS and Android deliver when the app is hidden.

## Weekly update workflow

1. Plan → **Update this week** (or Continue / Review).
2. **Copy previous week** (or Start from my plan). Values come from the last
   confirmed week, else the latest real record, else an undated import, else
   the plan (`from plan`), else blank. Every session starts *Not recorded*.
3. Change only what differs; changed rows are highlighted with `was …`.
4. Mark sessions Done / Partly done / Skipped (or **Mark all as done**), and
   confirm the day trained (prefilled from the day's weekday name or preferred
   days; required).
5. **Review changes** (optional): status per session, what changed, empty rows
   that won't be recorded, issues, and "Update my note to this week's loads".
6. **Confirm week** → workout records written in one transaction → review.

Integrity rules (unit-tested): copied ≠ confirmed; skipped / not-recorded never
complete; blank rows are never "unchanged"; one record per week; re-confirming
updates the same records and keeps the previous version; a session logged live
is shown as "Logged in detail" and counted once (`dedupeSessions` also guards
analysis if both exist).

## Notes import parser — capabilities and limitations

Understands: day headings (weekday names, `Day 2`, `UPPER BODY`, `#`, `:`),
date headings (`12 Oct 2026`, `2026-10-12`, `12/10/2026`; a date without a year
is never completed), exercise names (library names and aliases, custom names,
ambiguous names offer choices), kg / lb, per side (`/side`, `a side`, `each side`),
per dumbbell (`each hand`, `/dumbbell`, `dbs`, `each`), total (`total`, or
machines that are total by default), bodyweight (`BW`), added load (`BW+10kg`),
assistance, sets × reps (`3x8`, `3 × 8–12`, `3 sets of 8`, `3 sets × 8 reps`),
rep lists (`8 8 7`, `9, 8, 8`, `8/8/7`, `× 9, 8, 8`), reversed notation (`10x3`
is read as 3 sets of 10 **and flagged**), timed work (`3x45s`, `45s`, `1 min`),
bullets, comments (attached to the exercise above; after a blank line, to the day),
"not completed / skipped".

**V0.5 additions.** Exercise *blocks* (a name line, then detail lines such as
`27.5kg for 7 reps`, `4 × 6`, `76kg`, `Rest: 2 min`, combined by `mergeValues`);
gym shorthand in names (`exerciseKey`: db, bb, OHP, lat pd, lats pull down, flat
press…); a separate record of what was *done* (`performed`, `reps`, per-set
`loads`) next to the plan (sets × rep range); per-set loads (`60x8, 65x6, 70x5`,
`40/42.5/45kg x 8/6/5`, `Set 1: 100kg x 5`); `3x8 @ 60kg`; rest times saved to
the exercise; RPE/RIR, warm-ups, drop sets, superset labels and bracketed notes
kept as text; checkbox/emoji bullets; cardio and distance (distance is never
turned into time); a unitless load takes the note's unit only when every other
load agrees, and says so. A 35-note corpus test (`tests/unit/v5-notes-corpus.test.ts`)
enforces three invariants on every note: no input line is lost, nothing is
invented, and every guess is visible for review.

Limitations: one exercise per line (`squats 3x5, bench 3x8` on one line is kept
as text); supersets written `A + B` become one custom exercise; no fuzzy spelling
correction (unknown names become custom exercises); no bar or plate weight is
ever assumed; English only. Anything not understood is kept as note text and
never used for analysis.

## Performance analysis

- Only the same exercise with the same loading convention is compared
  (`comparableKey`); no bar weight is assumed and machines/Smith/dumbbells are
  never treated as equivalent.
- Change between two records: load up / reps up (best set, or total across the
  same sets at the same load) / more sets / easier (RIR) / stable / lower.
  `describeChange` explains it, e.g. "1 more rep in the first set at the same
  recorded load (30 kg/side)." No percentages are claimed.
- Status per exercise: *Improving* (last record improved), *Possible decline*
  (last two below the earlier best — one bad session never qualifies),
  *Possible plateau* (plateau rules below), *Stable*, *Not enough data* (< 2
  records, missing loads, or not comparable).
- Personal bests, milestones (new bests, heavier loads, more reps, weeks with
  every planned session done — counted, never a streak — 4-week blocks, and a
  bodyweight trend only when it matches the stated goal), weekly frequency.
- Charts: working load, total reps, volume (only for total / per-side /
  per-dumbbell, never across conventions), bodyweight, sessions per week.

## Coaching logic

- Weekly review (after confirming): sessions done of planned, per-exercise
  change, then 2–4 sentences: what improved, what's stable, sessions completed,
  and whether a change is justified. Rules: a plateau suggestion exists → say so
  (nothing changes without Accept); a session was missed → "continue the
  programme before considering a change"; otherwise "keep following" or "not
  enough evidence". Built only from confirmed records; reproducible.
- Plateau detection (unchanged V0.2 rules): ≥ 4 comparable sessions over ≥ 14
  days in a 6-week window, no long gap, no improvement on the earlier best. Up
  to two questions (sleep, effort, missed sessions, fatigue, food). Suggestions:
  continue, check consistency, review recovery, lighter week (−1 set), widen the
  rep range; programme changes only on Accept.
- Training + nutrition context (V0.3) and the "short on time this week" planner
  remain, behind Coach. Nutrition is never required.
